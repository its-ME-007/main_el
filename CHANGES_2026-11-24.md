## 2. Parallel benchmark (Phase 5)

`uv run python -m urban.parallel hebbal --n 16 --workers 2,4,8`, macro, 17 scenarios. I ran it with the
pre-resume version of `parallel.py`; the numbers are the same either way.

| P | wall | speedup | efficiency | scen/min | identical |
|---|---|---|---|---|---|
| 1 | 602 s | 1.00 | 100 % | 1.69 | ✓ |
| 2 | 312 s | 1.93 | 96 % | 3.26 | ✓ |
| 4 | 188 s | 3.20 | 80 % | 5.42 | ✓ |
| 8 | 161 s | 3.75 | 47 % | 6.35 | ✓ |

Your run on 16 cores: P=2 2.00, P=4 3.62. On the Mac, scaling flattens at 8 workers. Three causes show in the data:

- **Core types:** the M3 has 4 performance cores and 4 efficiency cores.
- **Contention:** time per run rose from 35 s to 66 s at P=8, as runs competed for memory and cache on 8 GB.
- **Load imbalance:** scenarios take 21–71 s, so utilisation fell to 0.87.

That's a good paragraph for the PAGP report: both machines appear, and the efficiency drop has an explanation.

## 3. Backend changes (small, defaults unchanged)

| File | Change |
|---|---|
| `urban/fcd.py` (new) | Vehicle trajectories for the animation. One micro run per scenario with `--fcd-output --fcd-output.geo`, sampled every 2 s for sim time 1200–1800 s, cut to the box plus 150 m. Writes `data/<area>/traffic_<run>.json` (frames of `[idx, x, z, angle, kmh, onCandidate]` in the UI's metric frame) and `traffic.json`. `uv run python -m urban.fcd hebbal --cands 39`: about 22 s per run, 2.6–2.9 MB each. The run stops at 1800 s, so its trip metrics are partial: use them for display only, never for scores. |
| `urban/sim.py` | `run(..., end=None)`: optional stop time; the default is still `DURATION * 2`. Needed because SUMO has no `--device.fcd.end` and rejects `--end` twice. |
| `urban/noise.py` | `summary()` also returns the seed means of `dQ` (and `dQ_sd`), plus `dC`, `L` and `P` (fixed per candidate), so the UI can re-score the 5-seed average with the user's weights. I checked that c39 rescores to +10.05, the same as the backend. |

## 4. Frontend changes

All of these are in `frontend/src/`.

**Results**
- **Results toggle: Macro screen (40) | Micro check (10).** This drives the ranking, the scores, the map colours,
  the chart, the hover card and the card headline.
  - Micro view: ranks only the 10 validated candidates by the 5-seed mean, re-scored with the current weights. The
    other 30 are listed below as "not checked in micro".
  - Macro view: all 40, ranked by the macro score.
- The candidate card leads with the 5-seed score (± sd) and notes the macro screen score. The score breakdown uses
  the 5-seed average.
- The "pass micro check" tile counts only candidates that are better and a real effect: 1/10, c39.
- Macro labels: "macro" replaces "meso" everywhere (your TODO in `data.js`).
- Short ranking tags: better, worse, no effect.

**Parallel tab** (`ParallelChart.jsx`)
- Speedup against the ideal S = P line, with a hover tooltip.
- A table of wall time, speedup, efficiency and throughput.
- A banner: "results identical to sequential".
- It shows even before candidate results exist.

**3D bridges** (`scene.js`)
- Candidates with `road_crossings + worksite_crossings > 0` (32 of 40) are drawn as raised decks.
- The deck is a level cross-section with parapets, swept along the line, at 6.5 m clearance with smoothstep ramps.
  Short links get steep ramps, which honestly shows they are hard to build.
- Piers are one `InstancedMesh` per bridge.
- With a candidate selected, only its bridge (and the hovered one) shows, and the camera flies in low for bridges.
- Layer toggle: "Bridges".

**Hover**
- The hovered candidate lifts a little with an animation, gets a pulsing outline, and the others fade back.
- Its bridge deck glows in the score colour.
- The hover card shows the name, a tag, score and rank, the delay and queueing change, veh/h, and how it is built
  (length, bridge or at grade, metro crossings, buildings).

**Animated vehicles** (`traffic.js`, `TrafficPanel.jsx`)
- All cars are one `InstancedMesh` with per-instance colour by speed, using the same scale as the roads.
- Position and heading are interpolated between the 2 s samples.
- Cars scale up with camera distance so they stay visible.
- Controls: Off / Baseline / With c39, play and pause, 1× to 30× speed, and a time slider. Switching run keeps the
  clock, so before and after line up.
- Cars on the candidate ride on its bridge deck, since SUMO has no heights.
- "Highlight cars that use c39" colours their whole trip cyan, with a counter. 27 cars in 10 min, about 160 veh/h,
  consistent with 188 veh/h from noise.

**GLSL shaders** (`scene.js`)
- **Roads use a custom `ShaderMaterial`.** Per vertex: two colours and two speeds (before and after) plus the
  distance along the road. Uniforms: `uTime`, `uMix` and `uFlow`.
  - The fragment shader draws dashes moving in the direction of travel at 2.5× the simulated speed. Jammed roads
    crawl and empty roads stay still.
  - The before/after switch is now a GPU blend: the buttons ease it, and a new Before ⟷ After slider scrubs it.
  - Layer toggle: "Traffic flow animation".
- **Candidates:** GLSL injected with `onBeforeCompile` gives scrolling diagonal "planned road" stripes, while the
  built-in colour, opacity and hover keep working.

**Tried and removed:** WebXR VR mode (#5), with a tabletop model and controller rays. It worked in Meta's Immersive
Web Emulator, but setup and aiming were too complicated for a demo, so I deleted all of it. Nothing is left in the code.

Checked: the production build compiles. I also rendered the page in a headless Chrome (swiftshader WebGL) with no
shader or runtime errors, for both the normal view and a `?cand=39` view.

## Review notes (please check)

1. **`parallel.py`, bug in the resume path (fixed).** The print after a reused round used `wall`, which is only set
   when a round actually runs. A resumed P=1 would raise `NameError`, and a later reused round would print the
   previous round's time. I changed it to `r['wall_s']`; that's the only change to your file.
2. **Scoring in the micro view** is the mean of the 5 seeds under the current weights: all terms are linear, so this
   equals the mean of the per-seed scores. "Pass" also requires `verdict == "real effect"`, so c19 (+0.2, noise)
   does not count.
3. **Bridge heights and ramp grades are illustrative.** They are not part of the score; P still prices crossings.
4. **Macro per-road stats:** `waiting` is 0 and `occupancy` holds v/c in %. The UI uses `time_loss`, `speed_rel` and
   `speed`, so nothing reads those two for macro.
5. **Not committed (gitignored `data/`):** the exports and `traffic_*.json`. After pulling, run the commands below.
   Old pre-fix results are archived locally in `data/hebbal/archive_v1_default_speeds/`.

## Run it

```bash
cd backend
uv run python -m urban.sim hebbal && uv run python -m urban.candidates hebbal

uv run python -m urban.export hebbal
cd ../frontend && npm install && npm run dev                            # http://localhost:5173
```

Before ⟷ After slider, then switch to Macro screen (c17 on top), then the Parallel tab.
